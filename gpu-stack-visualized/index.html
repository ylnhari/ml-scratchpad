One request, every layer

A user types "Explain GPUs" into a chat app. Between that and the first word of the answer, the request passes through about a dozen layers of software and hardware. Each layer turns what it receives into something simpler for the layer below, until it becomes instructions running on the GPU's cores. Then the result climbs back up.

PART I

Software

Everything that runs on CPUs: it decides what the GPU must compute and hands it over as a stream of small programs called kernels.

01

API and serving: getting the request to a GPU

Your app sends an HTTP POST, usually in the OpenAI chat format, to an endpoint. Behind it, a serving system such as Ray Serve (the engine behind Anyscale's hosted endpoints) runs several replicas: identical copies of the model server, each owning one or more GPUs. A router picks a replica for every request, and an autoscaler adds or removes replicas as traffic changes.

  • The router can be smarter than round-robin: Ray Serve LLM ships a router that prefers the replica that already holds this prompt's prefix in its KV cache, so that work is not repeated.
  • The answer streams back token by token over the same connection (server-sent events), so the user sees words as soon as they exist.

02

The inference engine: vLLM, one step at a time

Inside each replica runs an inference engine such as vLLM. It works in a loop of steps: every step, it picks which requests to advance, runs the model once for all of them together, and emits one new token for each. vLLM splits this across processes so the slow CPU work never blocks the GPU:

  • the API server process turns text into token IDs (tokenizing) and token IDs back into text (detokenizing), and streams results out;
  • the EngineCore process runs the scheduler and the KV cache manager; the two processes talk over ZeroMQ, a fast messaging library;
  • one GPU worker per GPU runs the model runner, which builds the input tensors and calls the model.

03

PyTorch: from model.forward() to kernel launches

The model runner calls model(input_ids, positions, …). That Python code never touches the GPU's numbers itself. Each tensor operation goes to PyTorch's C++ core, where a dispatcher looks at the tensors (which device, which data type) and picks the matching implementation. For a CUDA tensor that ends in a kernel launch: a request to run one small GPU program on the data.

  • Launches are asynchronous. The CPU puts each launch into a queue called a CUDA stream and moves on at once; the GPU works through the queue in order. The CPU only waits when it needs a result back, for example the sampled token.
  • In inference the model runs under torch.inference_mode(), so the dispatcher skips the autograd bookkeeping that training needs.
  • torch.compile can trace the model ahead of time and fuse chains of small element-wise ops into one generated kernel (written in Triton), so fewer kernels are launched.

04

Kernel libraries: who writes the GPU code

Almost nobody writes the heavy kernels by hand for each model. PyTorch and vLLM call into specialised libraries, each tuned for one kind of work. Click a part of one transformer layer to see which library runs it and what kind of kernel it is.

  • cuBLAS (and NVIDIA's open template library CUTLASS, on which many custom kernels are built): matrix multiplications, called GEMMs. They hold almost all of the model's arithmetic.
  • FlashAttention / FlashInfer: fused attention kernels that read the KV cache in blocks (section 09 explains why fusing matters).
  • Triton or hand-written CUDA: the small element-wise and normalisation kernels (RMSNorm, RoPE, activation, residual add).
  • NCCL (NVIDIA Collective Communications Library): All-Reduce and the other collectives when a model is split across GPUs.
  • cuDNN: NVIDIA's deep-learning primitives library, best known for convolutions; it also offers fused attention kernels.
05

CUDA: a kernel is a grid of blocks of threads

CUDA is NVIDIA's programming model and toolkit for GPUs. A kernel is a function that runs on the GPU. When it is launched, it runs as thousands of threads, all executing the same code on different data. The threads are grouped in two levels:

  • a thread block (up to 1,024 threads) always runs on one SM and can share fast on-chip memory and synchronise inside the block;
  • the grid is all the blocks of one launch. Blocks cannot rely on each other: the hardware may run them in any order, on any SM.

The launch states both sizes: kernel<<<grid, block, shared_mem, stream>>>(args). Inside, each thread works out which piece of data is its own from its block and thread numbers. The hardware then cuts every block into warps of 32 consecutive threads (section 08).

06

From C++ to GPU instructions: PTX and SASS

GPU code is compiled in two stages. The compiler nvcc turns CUDA C++ into PTX (Parallel Thread Execution), a virtual instruction set that is the same for every NVIDIA GPU. A second assembler, ptxas, turns PTX into SASS, the real machine code of one GPU generation (sm_90 for the H100). Libraries ship both: SASS for the GPUs they were built for, and PTX so the driver can compile it on the fly (just-in-time) for a newer GPU.

PART II

Hardware

What the GPU is made of, and what happens on it once a kernel arrives. Numbers are for an NVIDIA H100 SXM5, the most common GPU in today's LLM servers.

07

Inside an H100: GPCs, SMs and cores

A GPU is not one big processor but many copies of the same building block, the streaming multiprocessor (SM). An H100 SXM5 has 132 SMs, grouped into 8 GPCs (graphics processing clusters). They share a 50 MB L2 cache and 80 GB of HBM3 memory. Zoom in level by level:

08

Warps and the scheduler: how an SM hides waiting

The warp, 32 threads, is the unit the hardware actually schedules. All 32 run the same instruction at the same time on their own data (NVIDIA calls this SIMT, single instruction, multiple threads). Each of an SM's 4 partitions has a warp scheduler that, every clock cycle, picks one warp that is ready and issues its next instruction.

Reading memory takes hundreds of cycles. A CPU core would mostly sit and wait. An SM keeps many warps resident (up to 64) and simply switches to another ready warp at no cost, so the arithmetic units stay busy while others wait. Press Play and compare few warps with many.

09

The memory hierarchy: small and fast near the cores, big and slow far away

Data reaches the tensor cores through a ladder of memories. Each step up is smaller but closer and faster. Fast kernels are built around one idea: load each number from far memory once, keep it close, and reuse it as many times as possible.

10

One matrix multiply on the chip

Take one linear layer: C = A · B, where A holds the tokens' activations and B is a weight matrix. A GEMM kernel cuts C into tiles, and each tile becomes one thread block. The blocks are spread over the 132 SMs. Inside its SM, a block walks along the shared dimension: it copies a slice of A and a slice of B from HBM into shared memory, the tensor cores multiply them, and the partial sums build up in registers. At the end the finished tile is written back to HBM.

11

Compute-bound or memory-bound? The roofline

Every kernel needs two things: arithmetic (FLOPs, floating-point operations) and bytes moved from HBM. Their ratio, FLOPs per byte, is the kernel's arithmetic intensity. An H100 SXM5 can do about 989 trillion BF16 FLOPs per second on its tensor cores but read only about 3.35 TB per second from HBM, so a kernel needs about 295 FLOPs per byte before the tensor cores, not memory, become the limit.

For a weight matrix multiplied by the activations of n tokens, each weight is read once and used n times, so intensity grows with n. Drag n: one decode step for a single request (n = 1) is deep in the memory-bound zone; a long prefill is compute-bound. This is the hardware reason behind batching.

12

One decode step, kernel by kernel

Putting it together: one decode step of a Llama-style model is a long chain of small kernels, about a dozen per layer (norms, GEMMs, RoPE, attention, activation, adds) times every layer. For one token each kernel finishes in microseconds, so the CPU time spent launching them can leave the GPU idle between kernels. CUDA graphs fix this: the engine records the whole chain once, then replays it with a single launch. vLLM captures graphs for its common batch sizes at start-up.

EXTRAS

Terms

X1

Glossary

SM (streaming multiprocessor)
The GPU's building block: a small processor with its own warp schedulers, cores, tensor cores, registers and shared memory. An H100 SXM5 has 132.
warp
32 threads that the hardware schedules together; all execute the same instruction at the same time.
kernel
A function that runs on the GPU, launched as a grid of thread blocks.
thread block
A group of up to 1,024 threads that runs on one SM and can share shared memory.
GEMM
General matrix-matrix multiply: the operation behind every linear layer.
tensor cores
Units inside each SM that multiply small matrices in one instruction; where almost all of an LLM's FLOPs run.
HBM
High-bandwidth memory: the GPU's main memory (80 GB on an H100), stacked next to the chip.
L2 cache
A 50 MB on-chip cache shared by all SMs; every HBM read passes through it.
shared memory
A fast scratchpad inside each SM, controlled by the kernel, shared by the threads of a block.
TMA
Tensor Memory Accelerator: an H100 unit that copies tiles between HBM and shared memory in the background.
CUDA stream
A queue of GPU work. Launches go in at one end; the GPU runs them in order.
CUDA graph
A recorded chain of kernel launches that can be replayed with one launch.
PTX
Parallel Thread Execution: NVIDIA's virtual instruction set, compiled to SASS for each GPU.
SASS
The real machine code of one GPU generation.
cuBLAS
NVIDIA's library of tuned linear-algebra kernels, including GEMM.
NCCL
NVIDIA Collective Communications Library: All-Reduce and other multi-GPU collectives.
dispatcher
The part of PyTorch that picks which implementation of an op to run, from the tensors' device and data type.
replica
One full copy of the model server, with its own GPUs.
memory-bound
Limited by how fast data arrives from memory, not by arithmetic.
compute-bound
Limited by arithmetic speed; data arrives fast enough.
FLOPs
Floating-point operations: multiplications and additions.
KV cache
The saved keys and values of earlier tokens, so they are not recomputed each step.
All-Reduce
A collective where every GPU contributes a partial result and every GPU ends up with the sum.
logits
The model's raw scores, one per vocabulary entry, before softmax.
