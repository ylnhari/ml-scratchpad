PART I

Software

Everything that runs on the CPU. It decides what the GPU must compute and hands it over as a stream of small GPU programs called kernels.

01

The loop on the CPU: training step and inference step

Every AI workload is a loop that the CPU drives. The framework (PyTorch, JAX or TensorFlow) or an inference server built on one (vLLM, SGLang, TensorRT-LLM) runs the loop; each turn of the loop is one long list of GPU kernels. The two loops differ only at the top.

02

From a framework call to a kernel launch

Model code never touches the GPU's numbers itself. Follow one matrix multiply, y = x @ W, from Python to the GPU. The example is PyTorch; JAX and TensorFlow differ mainly in the middle, where a compiler (XLA) first turns the whole program into a graph and then into kernels.

  • Launches are asynchronous: the CPU puts each one in a queue called a CUDA stream and moves on at once. It waits only when it needs a result back.
  • Compilers (torch.compile, XLA, TensorRT) look at many ops together and fuse chains of small ones into one kernel, so fewer kernels run and less data moves (section 14).
speed
03

Kernel libraries: who writes the GPU code

Frameworks rarely contain the heavy GPU code themselves. They call specialised libraries, each tuned for one kind of work. Click a part of one transformer layer to see which library runs it.

  • cuBLAS, and NVIDIA's open template library CUTLASS on which many custom kernels are built: matrix multiplications (GEMMs), which hold almost all of the arithmetic.
  • cuDNN: NVIDIA's deep-learning primitives, best known for convolutions; it also has fused attention.
  • FlashAttention / FlashInfer: fused attention kernels that keep their working data on-chip (section 09).
  • Triton (a Python-like language that compiles to GPU kernels) or hand-written CUDA: small element-wise kernels such as normalisation and activation functions.
  • NCCL (NVIDIA Collective Communications Library): All-Reduce and the other operations that move data between GPUs (section 16).
PART II

CUDA

CUDA is NVIDIA's programming model and toolkit: how GPU programs are written, compiled and launched.

04

A kernel is a grid of blocks of threads

A kernel runs as thousands of threads, all executing the same code on different data, grouped in two levels:

  • a thread block (up to 1,024 threads) always runs on one SM, and its threads can share fast on-chip memory and wait for each other;
  • the grid is all the blocks of one launch. Blocks cannot rely on each other: the hardware may run them in any order, on any SM. (Hopper adds thread block clusters: a few blocks on neighbouring SMs that can share memory.)

The launch states both sizes: kernel<<<grid, block, shared_mem, stream>>>(args). The hardware then cuts every block into warps of 32 consecutive threads (section 08).

05

From C++ to GPU instructions: PTX and SASS

GPU code is compiled in two stages. The compiler nvcc turns CUDA C++ into PTX (Parallel Thread Execution), a virtual instruction set that stays stable across GPU generations. A second assembler, ptxas, turns PTX into SASS, the real machine code of one GPU generation (sm_90 for the H100). Libraries ship SASS for the GPUs they support plus PTX, which the driver can compile just in time for a newer GPU (except architecture-specific targets such as sm_90a, which Hopper's fastest kernels use).

06

Streams, launches and copies

The CPU and GPU run side by side. The CPU fills streams, queues of work; the GPU takes work from them in order. Kernels in different streams may run at the same time, and data copies between CPU memory and GPU memory are done by separate copy engines, so they can overlap with computation.

PART III

One GPU

What the GPU is made of and what happens on it once a kernel arrives. Numbers are for an NVIDIA H100 SXM5, a widely deployed GPU for training and serving.

07

Inside an H100: GPCs, SMs and cores

A GPU is many copies of one building block, the streaming multiprocessor (SM). An H100 SXM5 has 132 SMs, grouped into 8 GPCs (graphics processing clusters). They share a 50 MB L2 cache (a fast on-chip memory) and 80 GB of HBM3 (high-bandwidth memory). Zoom in level by level:

08

Warps and the scheduler: how an SM hides waiting

The warp, 32 threads, is the unit the hardware schedules. All 32 run the same instruction at the same time on their own data (NVIDIA calls this SIMT, single instruction, multiple threads). Each of an SM's 4 partitions has a warp scheduler that, every clock cycle, picks one ready warp and issues its next instruction.

Reading memory takes hundreds of cycles. An SM keeps many warps resident (up to 64) and simply switches to another ready warp at no cost, so the arithmetic units stay busy while others wait. Press Play and compare few warps with many.

09

The memory hierarchy

Data reaches the tensor cores through a ladder of memories. Each step up is smaller but closer and faster. Fast kernels are built around one idea: load each number from far memory once, keep it close, and reuse it as many times as possible. Click a level.

10

How a load reaches HBM: coalescing and bank conflicts

When a warp loads data, the hardware gathers the 32 threads' addresses and fetches whole aligned pieces of memory: 32-byte sectors, grouped into 128-byte cache lines. If the 32 threads read 32 neighbouring 4-byte numbers, that is exactly one 128-byte line: the load is coalesced and every byte fetched is used. Scattered addresses fetch many sectors and waste most of them. Shared memory has its own rule: it is split into 32 banks, and two threads hitting different addresses in the same bank must take turns.

11

One matrix multiply on the chip

Take one linear layer: C = A · B, where A holds the tokens' activations and B is a weight matrix. A GEMM kernel cuts C into tiles, and each tile becomes one thread block. The blocks are spread over the 132 SMs. Inside its SM, a block walks along the shared dimension: it copies a slice of A and a slice of B from HBM into shared memory, the tensor cores multiply them, and the partial sums build up in registers. At the end the finished tile is written back to HBM.

12

Compute-bound or memory-bound? The roofline

Every kernel needs arithmetic (FLOPs, floating-point operations) and bytes moved from HBM. Their ratio, FLOPs per byte, is its arithmetic intensity. An H100 SXM5 can do about 989 trillion BF16 (bfloat16, a 2-byte number format) FLOPs per second on its tensor cores but read only about 3.35 TB per second from HBM, so a kernel needs about 295 FLOPs per byte before the tensor cores, not memory, become the limit.

For a weight matrix multiplied by the activations of n tokens, each weight is read once and used n times, so intensity grows with n. Drag n: one inference step for a single request (n = 1) is deep in the memory-bound zone; a training batch or a long prompt is compute-bound.

14

Kernel fusion: stop the round trips to HBM

Small element-wise ops do only a few FLOPs per number, so they are memory-bound: their time is the time to read and write HBM. Run three of them as separate kernels and every intermediate result is written to HBM and read back. Fuse them into one kernel and the data is read once, kept in registers through all three steps, and written once. Example: a residual add, then RMSNorm (rescale each token's numbers), then a multiply by one scale factor, on a [tokens × 4,096] BF16 tensor.

PART V

Many GPUs

Big models are trained, and often served, on many GPUs at once. Then the speed of the links between GPUs matters as much as the GPUs themselves.

15

Inside a server: NVLink, NVSwitch, PCIe and the network

An 8-GPU server such as the DGX H100 connects its GPUs in three different ways. Click a link type to follow a byte:

  • NVLink: each H100 has 18 NVLink connections, 900 GB/s in total (450 GB/s each way), going to NVSwitch chips (4 in a DGX H100) that let every GPU talk to every other at full speed.
  • PCIe: the slower link to the CPUs and their memory, used for loading data and model weights.
  • Network cards (ConnectX-7, 400 Gb/s each, one per GPU) on InfiniBand or Ethernet: the only way out of the server, about 9 times slower per GPU than NVLink.
16

How GPUs add up their results: ring All-Reduce

In training, every GPU computes gradients on its own data, and all of them need the sum. In tensor-parallel inference, every GPU holds part of a layer's output and all need the total. Both use All-Reduce. NCCL's ring version splits the data into one chunk per GPU and passes chunks around a ring in two phases: reduce-scatter (each GPU ends up owning the full sum of one chunk) then all-gather (everyone receives every finished chunk). Each GPU sends and receives about 2 × (N−1)/N of the data, no matter how many GPUs there are.

17

Racks and clusters

Zoom out. GPUs inside one NVLink domain talk fast; beyond it, traffic goes over the network. Newer systems make that domain bigger: the GB200 NVL72 rack joins 72 Blackwell GPUs into one NVLink domain. Clusters then connect many servers or racks with a fat-tree network of switches.

PART VI

All together

One inference step and one training step, kernel by kernel, with everything above in play.

18

One inference step, kernel by kernel

One step of generating a token is a long chain of small kernels: about a dozen per layer (normalisations, GEMMs, attention, activation, adds) times every layer. Each finishes in microseconds, so the CPU time spent launching them can leave the GPU idle in between. CUDA graphs fix this: the program records the chain once and replays it with a single launch. Serving engines record graphs for their common batch sizes at start-up. Timings in this figure are illustrative.

19

One training step on many GPUs

In data-parallel training every GPU runs forward and backward on its own batch, then the gradients are All-Reduced (section 16) and every GPU applies the same optimizer update. Done naively, the All-Reduce waits until backward ends. Frameworks instead group gradients into buckets and start each bucket's All-Reduce, on a separate NCCL stream, as soon as its layers' gradients are ready, so communication hides behind the rest of backward. Terms

X1

Glossary

SM (streaming multiprocessor)
The GPU's building block: a small processor with its own warp schedulers, cores, tensor cores, registers and shared memory. An H100 SXM5 has 132.
warp
32 threads that the hardware schedules together; all execute the same instruction at the same time.
kernel
A function that runs on the GPU, launched as a grid of thread blocks.
thread block
A group of up to 1,024 threads that runs on one SM and can share shared memory.
GEMM
General matrix-matrix multiply: the operation behind every linear layer.
tensor cores
Units inside each SM that multiply small matrices in one instruction; where almost all of an LLM's FLOPs run.
HBM
High-bandwidth memory: the GPU's main memory (80 GB on an H100), stacked next to the chip.
L2 cache
A 50 MB on-chip cache shared by all SMs; every HBM read passes through it.
shared memory
A fast scratchpad inside each SM, controlled by the kernel, shared by the threads of a block.
TMA
Tensor Memory Accelerator: an H100 unit that copies tiles between HBM and shared memory in the background.
CUDA stream
A queue of GPU work. Launches go in at one end; the GPU runs them in order.
CUDA graph
A recorded chain of kernel launches that can be replayed with one launch.
PTX
Parallel Thread Execution: NVIDIA's virtual instruction set, compiled to SASS for each GPU.
SASS
The real machine code of one GPU generation.
cuBLAS
NVIDIA's library of tuned linear-algebra kernels, including GEMM.
NCCL
NVIDIA Collective Communications Library: All-Reduce and other multi-GPU collectives.
dispatcher
The part of PyTorch that routes each op to an implementation, using the tensors' dispatch keys (backend such as CUDA, plus features such as autograd).
GPC
Graphics processing cluster: a group of SMs on the chip. An H100 SXM5 has 8.
SIMT
Single instruction, multiple threads: the 32 threads of a warp run the same instruction on their own data.
occupancy
How many warps are resident on an SM compared with the maximum (64). More warps give the scheduler more to switch between.
coalesced load
A warp load whose 32 addresses fall in as few 32-byte sectors as possible, so every fetched byte is used.
sector
The 32-byte unit in which the GPU fetches global memory; four make a 128-byte cache line.
bank conflict
Two threads of a warp hitting different addresses in the same one of shared memory's 32 banks; the accesses are serialised.
kernel fusion
Running several operations in one kernel so intermediate results stay in registers instead of going through HBM.
arithmetic intensity
FLOPs done per byte moved from memory. Below about 295 on an H100 a kernel is memory-bound.
copy engine
A GPU unit that copies data between CPU and GPU memory while the SMs compute.
NVLink
NVIDIA's direct GPU-to-GPU link: 900 GB/s total per H100 (450 GB/s each way).
NVSwitch
A switch chip that connects many GPUs' NVLinks so every GPU reaches every other at full speed.
PCIe
The standard expansion bus connecting GPUs to CPUs; Gen5 x16 is 64 GB/s each way.
NIC
Network interface card. A DGX H100 has a 400 Gb/s ConnectX-7 per GPU.
InfiniBand
A low-latency data-centre network commonly used between GPU servers.
GPUDirect RDMA
Lets a network card read and write GPU memory directly, without copying through CPU memory.
fat tree
A network of leaf and spine switches with enough links that every server can send at full speed at once.
DDP
PyTorch DistributedDataParallel: every GPU holds a full model copy and gradients are All-Reduced.
gradient
How much the loss would change for a small change in each weight; computed in the backward pass.
CUTLASS
NVIDIA's open-source C++ templates for writing fast GEMM and attention kernels.
Triton
A Python-like language and compiler for writing GPU kernels.
memory-bound
Limited by how fast data arrives from memory, not by arithmetic.
compute-bound
Limited by arithmetic speed; data arrives fast enough.
FLOPs
Floating-point operations: multiplications and additions.
KV cache
The saved keys and values of earlier tokens, so they are not recomputed each step.
All-Reduce
A collective where every GPU contributes a partial result and every GPU ends up with the sum.
logits
The model's raw scores, one per vocabulary entry, before softmax.
prefill
The first step for a request: its whole prompt is processed at once.
decode
Every later step: one new token per request.
BF16 (bfloat16)
A 2-byte floating-point format used for LLM weights and activations.
