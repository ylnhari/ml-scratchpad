PART I

The example and the cache

Every number on this page is computed from one setup by the code of the notebook this page is drawn from. A few words first.

token
a word or piece of a word, the unit the model reads and writes
GiB
230 bytes (MiB = 220, KiB = 210), the units vLLM's logs use
KV cache
the keys and values every earlier token left behind, kept on the GPU so they are not recomputed at each new token
block
vLLM stores the KV cache in fixed blocks of 16 tokens, so memory is handed out in small, equal pieces
util
--gpu-memory-utilization: the share of the GPU vLLM may use for everything

02
The KV cache, one token at a time

  
Every token a request has seen leaves a key and a value in every layer. Llama-3.1-8B has 32 layers, and 8 key/value heads of 128 numbers each (its 32 query heads share them, which is grouped-query attention).

  
So one token costs 2 × 8 × 128 × 2 bytes per layer, times 32 layers. Drag the slider to grow one request.

Sizing the KV pool

  
The pool is whatever is left under the budget: budget − weights − the measured activation peak − other workspaces. It is split into 16-token blocks, and vLLM prints two lines that summarise everything.

06
Many requests: the scheduler loop

  
Every step, vLLM's scheduler runs this loop, which the notebook implements in about 40 lines:

  
budget = max_num_batched_tokens
1. each RUNNING request gets 1 token (or its
   next prompt chunk); allocate a block if needed.
   No free block? PREEMPT the newest running
   request: free its blocks, re-queue it.
2. admit WAITING requests while budget and
   max_num_seqs allow (long prompts are chunked)
3. run ONE forward pass for everything scheduled
4. finished requests free all their blocks

07
The three concurrency limits

  
"How many users at once?" has several answers, and the smallest wins. Short requests hit --max-num-seqs; long ones run out of KV pool. --max-num-batched-tokens never limits how many run, only how fast prompts get in. The pool here follows the settings you chose in §04.

08
Why batching is nearly free

  
A decode step reads all 15 GiB of weights to produce one token per request. Reading them once for 1 request or for 256 costs about the same, so the step time barely moves while throughput climbs. Each user still sees about one token per step.
