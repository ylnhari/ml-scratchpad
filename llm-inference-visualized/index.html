00.1

The transformer, end to end

Every large language model you have used, including GPT, Llama, Claude, Gemini and Mistral, is built from this one diagram. Data flows from the bottom to the top. Press play to follow it, or click any part.

The 2017 Transformer was built for translation. It had two stacks: an encoder that read the source sentence, and a decoder that wrote the translation. GPT-style language models keep only the decoder stack, because their one job is to continue text. That decoder-only design is what you see here.

00.2

Attention, the core idea

Attention is how a word picks up meaning from the words before it. Every token produces three vectors from its own embedding:

  • a query: what am I looking for?
  • a key: what do I contain?
  • a value: what will I pass on if someone picks me?

The query is compared with every earlier key using a dot product. The scores are divided by √d to keep them in a sensible range, then turned into weights with softmax. The token's new vector is the weighted mix of the values.

Inference optimizations

How serving systems make inference fast and cheap, and which of those shapes or memory costs each technique attacks.

01

Prefill vs decode

Prefill pushes all prompt tokens through as one matrix–matrix product. Decode handles one token per step, a matrix–vector product, and still reads every weight.

02

KV cache memory

The KV cache grows linearly with batch × sequence length. Drag the sliders to see how it crowds the weights out of GPU memory.

03

Static vs in-flight batching

Four batch slots and twelve requests of different lengths. With static batching, a slot that finishes early sits idle. With in-flight batching, the next request takes over that slot straight away.

04

Model parallelism

One GPU is rarely enough. This chapter takes the strategies one at a time: why we need them, what each one splits, and what it costs. They all reuse the shapes from §00.3.

GPU 0 GPU 1 GPU 2 GPU 3 idle or wasted each GPU keeps its colour in every figure from here on · t = number of GPUs
Every strategy answers one question: which dimension of which tensor gets cut, and what must travel between GPUs as a result? DP cuts the batch b, PP cuts the layer stack, TP cuts the weights (and with them h, the heads and ffn), SP cuts the sequence s, and EP cuts the set of experts.
04.1

Why one GPU is not enough

Weights alone outgrow a GPU fast, and the KV cache from §02 comes on top. Parallelism serves three different goals, and each strategy helps only some of them.

precision
04.2

Data parallelism: copy the model, split the batch

The simplest strategy: every GPU holds a full copy, and requests are spread across them. It scales throughput almost perfectly, but only if the model fits on one GPU.

In training, DP replicas also All-Reduce their gradients after every step (see A1). At inference there is nothing to sync: replicas sit behind a load balancer.
04.3

Pipeline parallelism: split the layers

Cut the stack of layers into stages, one per GPU. Each GPU stores 1/p of the weights and passes only a small activation tensor [b, s, h] to the next stage. But stages must wait on each other, and a single request still has to walk through every stage in turn.

microbatches
Splitting the batch into microbatches keeps more stages busy at once and shrinks the idle "bubble", but never removes it. PP helps a model fit, and adds throughput once the pipeline is full. It does not make a single request faster.
04.4

Tensor parallelism: split inside each layer

TP splits the weight matrices themselves, so every GPU works on every layer, for the same sequences, with part of the weights. Step through what gets split, how, and what it costs.

04.5

Sequence parallelism: remove TP's copies

TP leaves LayerNorm and Dropout copied on every GPU. These ops treat each token on its own, so they can be split along the sequence s instead. Compare the possible layouts of the same [b, s, h] tensor on two GPUs:

05

MHA → GQA → MQA

Query heads keep their own projections, while K/V heads are shared across groups. Fewer KV heads means a smaller KV cache and fewer memory reads.

06

FlashAttention: tiling in SRAM

Standard attention writes the full N×N score matrix to HBM and reads it back. FlashAttention computes it tile by tile in on-chip SRAM and never stores it. The output is exactly the same.

07

PagedAttention: KV cache in blocks

There are 256 token slots of KV memory. Contiguous allocation reserves the maximum length (64) for every request. Paging hands out 8-token blocks on demand, from anywhere in memory.

08

Quantization

48 weights snapped to a grid of 2b levels. A single outlier stretches the grid and wipes out resolution for everything else. Clipping the range trades that rounding error for clipping error.

09

2:4 structured sparsity

In every group of 4 weights, the 2 smallest are zeroed. The GPU stores only the survivors plus a 2-bit position index for each.

Backward pass & training memory
