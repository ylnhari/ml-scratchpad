PART I

Foundations

What a language model is made of, how attention works, and the tensor shapes it moves around. Everything in Part II builds on this.

Three letters used on every figure

A model does not read letters. It cuts text into tokens, which are whole words or pieces of words, and works on one list of numbers per token. All of that fits in a block of numbers with three sides, and we write its shape as [b, s, h]:

b
batch: how many separate texts are processed together. For example, 2 users' prompts.
s
sequence length: how many tokens each text has. For example, 6 tokens: "I saw a dog ride in".
h
hidden size: how many numbers describe one token. For example, 4,096 in Llama 2 7B (drawn as 8 here).

So the input is b texts of s tokens each, and once inside the model every one of those tokens is h numbers long: a block of b × s × h numbers. Other letters are introduced where they first appear. In formulas, A·B between two matrices means matrix multiplication (each row of A combined with each column of B; Extras X4 explains it, along with the terms GEMM and GEMV), and a name followed by brackets, like act(U) or LN(X), means a function applied to that block, not a multiplication.

Every large language model you have used, including GPT, Llama, Claude, Gemini and Mistral, is built from this one diagram. Data flows from the bottom to the top. Press play to follow it, or click any part.

The 2017 Transformer was built for translation. It had two stacks: an encoder that read the source sentence, and a decoder that wrote the translation. GPT-style language models keep only the decoder stack, because their one job is to continue text. That decoder-only design is what you see here.

00.2

Attention, the core idea

Attention is how a word picks up meaning from the words before it. Every token produces three vectors from its own embedding, by multiplying it with three learned weight matrices, W_Q, W_K and W_V:

  • a query: what am I looking for?
  • a key: what do I contain?
  • a value: what will I pass on if someone picks me?

The query is compared with every earlier key using a dot product. The scores are divided by √d, where d is the length of the query and key vectors, to keep them in a sensible range, then turned into weights with softmax (Extras X3 shows how). The token's new vector is the weighted mix of the values. A model runs many heads like this side by side; their outputs are joined and mixed by one more learned matrix, W_O (section 00.3, step 9).

Two kinds of numbers appear. Weights (E, W_Q, W₁, W_U…) are learned once and stay fixed. Activations are the tensors computed from your input as it flows through (X, Q, K, V, the MLP's wide output, the logits); a new prompt gives new activations. Not the same thing as the activation function (act) inside the MLP.

PART II

Inference optimizations

How serving systems make inference fast and cheap, and which of those shapes or memory costs each technique attacks.

01

Prefill vs decode

Answering a request has two phases. Prefill reads the whole prompt at once, as one matrix–matrix product. Decode then writes the reply one token per step, a matrix–vector product that still reads every weight. It stops when the model emits an end-of-sequence token or reaches a length limit. Long prompts, such as retrieved documents added by RAG (retrieval-augmented generation), make prefill longer. Tokens per second compare fairly only between models with the same tokenizer, since tokenizers cut text differently.

speed
02

KV cache memory

Each token's keys and values (K and V, from section 00.2, Attention) are saved so later tokens do not recompute them. That store is the KV cache, and it grows linearly with batch × sequence length. Size per token = 2 (K and V) × layers × KV heads × d_head × bytes per number. For Llama 2 7B in FP16 that is 2 × 32 × 32 × 128 × 2 bytes = 0.5 MB per token, so one 4,096-token sequence needs about 2 GB next to 13.5 GB of weights. Drag the sliders to see how it crowds the weights out of GPU memory. Precision is how many bytes store each number: FP16 is a 16-bit floating-point number (2 bytes), FP8 an 8-bit one (1 byte), and INT8 or INT4 are 8- or 4-bit integers.

03

Static vs in-flight batching

Four batch slots and twelve requests of different lengths. With static batching, a slot that finishes early sits idle. With in-flight batching, the next request takes over that slot straight away.

speed

The same idea as a live server: requests arrive over time and wait in a queue, run in one of four slots, and leave when their reply is finished. Switch between the two policies and watch how long requests wait.

04

Model parallelism

One GPU is rarely enough. This chapter takes the strategies one at a time: why we need them, what each one splits, and what it costs. They all reuse the shapes from section 00.3 (Follow the shapes).

GPU 0 GPU 1 GPU 2 GPU 3 idle or wasted each GPU keeps its colour in every figure from here on · t = number of GPUs
Every strategy answers one question: which dimension of which tensor gets cut, and what must travel between GPUs as a result? Data parallelism (DP) cuts the batch b, pipeline parallelism (PP) cuts the layer stack, tensor parallelism (TP) cuts the weights (and with them h, the heads and ffn), sequence parallelism (SP) cuts the sequence s, and expert parallelism (EP) cuts the set of experts in a mixture-of-experts model (section A2).
04.1

Why one GPU is not enough

Weights alone outgrow a GPU fast, and the KV cache from section 02 (KV cache memory) comes on top. Parallelism serves three different goals, and each strategy helps only some of them.

precision
04.2

Data parallelism: copy the model, split the batch

The simplest strategy: every GPU holds a full copy, and requests are spread across them. It scales throughput almost perfectly, but only if the model fits on one GPU.

speed
In training, the copies also add up their gradients across GPUs after every step, a step called an All-Reduce (section 04.4 shows it; section A1 covers training). At inference there is nothing to sync: replicas sit behind a load balancer.
04.3

Pipeline parallelism: split the layers

Cut the stack of layers into stages, one per GPU. Each of the p GPUs stores 1/p of the weights and passes only a small activation tensor [b, s, h] to the next stage. But stages must wait on each other, and a single request still has to walk through every stage in turn.

More microbatches make each block smaller and let the stages overlap, so the run finishes earlier.

microbatches
Splitting the batch into microbatches keeps more stages busy at once and shrinks the idle "bubble", but never removes it. PP helps a model fit, and adds throughput once the pipeline is full. It does not make a single request faster.
04.4

Tensor parallelism: split inside each layer

TP splits the weight matrices themselves, so every GPU works on every layer, for the same sequences, with part of the weights. Step through what gets split, how, and what it costs.

speed
04.5

Sequence parallelism: remove TP's copies

TP leaves LayerNorm and Dropout (a training-only step that randomly zeroes some values) copied on every GPU. These ops treat each token on its own, so they can be split along the sequence s instead. Inside every layer, TP + SP switches layout op by op: split s at LayerNorm, Dropout and the residual add; plain TP inside attention and the MLP. 05

MHA → GQA → MQA

In standard multi-head attention (MHA), every query head has its own key and value head. Grouped-query attention (GQA) lets a group of query heads share one, and multi-query attention (MQA) shares one across all of them. Fewer KV heads means a smaller KV cache and fewer memory reads. The sharing must be learned: a model is trained with GQA or MQA, or an existing MHA model is uptrained with a small fraction of its original training compute. MQA can lose some quality, which is why most current models use GQA (Llama 2 70B: 64 query heads, 8 KV heads).

Where do fewer K and V heads come from? From smaller weight matrices. Section 00.2 used standard MHA, where W_Q, W_K and W_V are all [h, h]: each head owns a d_head-wide slice of columns. GQA keeps every slice of W_Q but gives W_K and W_V only one slice per group, so they are narrower and K and V come out smaller. You can also read each slice as one head's own small matrix: 8 W_Q matrices but only 2 W_K and 2 W_V for GQA with 2 groups. Same picked variant as above:

06

FlashAttention: tiling in SRAM

A GPU has two kinds of memory: a large but slow main memory (HBM) and a tiny but very fast on-chip memory (SRAM). Standard attention writes the full s × s table of scores to HBM and reads it back. FlashAttention computes it one small tile at a time in SRAM and never stores the whole table. The output is exactly the same.

speed
07

PagedAttention: KV cache in blocks

There are 256 token slots of KV memory. Contiguous allocation reserves the maximum length (64) for every request. Paging hands out 8-token blocks on demand, from anywhere in memory. Reserving the maximum wastes memory three ways: over-provisioning (slots kept for tokens that are never generated), internal fragmentation (the unused tail of a reservation) and external fragmentation (free gaps too small for a new request). With paging, each request keeps a block table that maps its blocks, in order, to wherever they sit in memory.

See it at full scale: vLLM Memory, Visualized sizes a real KV pool (27,635 blocks of 16 tokens) and runs vLLM's scheduler over it, with the Python behind every figure runnable in the page.

08

Quantization

Quantization stores each number with fewer bits, so it can only take a few evenly spaced values: 16 with 4 bits, 256 with 8. Here 48 weights are snapped to the nearest one. A single outlier stretches the grid and wipes out resolution for everything else. Clipping the range trades that rounding error for clipping error.

09

Pruning

Pruning removes weights that matter least, usually the ones closest to zero, by setting them to exactly 0. The model gets smaller and, if the hardware can skip the zeros, faster. It is not quantization (section 08): quantization keeps every weight but stores it with fewer bits, while pruning deletes weights and keeps the rest at full precision. The two stack, so a pruned model can also be quantized.

  • Unstructured pruning zeroes any weight anywhere. It can remove a lot, but the zeros are scattered, so GPUs cannot skip them and it rarely runs faster.
  • Structured pruning zeroes weights in a fixed pattern the hardware understands, so it does run faster.

2:4 structured sparsity is the pattern NVIDIA GPUs accelerate: in every group of 4 weights, the 2 smallest are zeroed. The GPU stores only the 2 survivors plus a 2-bit position index for each, and skips the zeros in the matrix multiply.

Speculative decoding

A small draft model guesses several tokens. The big model checks all of them in a single parallel pass and keeps the matching prefix, plus one token of its own. It is also called speculative sampling or assisted generation. The draft can be a separate small model, or extra prediction heads added to the big model itself (as in Medusa).

12

Disaggregated serving: prefill and decode on different GPUs

Section 01 showed the two phases need different things: prefill is compute-bound, decode is memory-bound. When both run on the same GPU, a new prompt's prefill takes the GPU over and every running request stops getting tokens until it finishes. Disaggregated serving gives prefill and decode their own GPUs and ships each request's KV cache (section 02) from the prefill GPU to the decode GPU once its prompt is done.

  • Aggregated (the usual setup, with in-flight batching from section 03): both GPUs do both jobs.
  • Disaggregated: GPU 0 only prefills, GPU 1 only decodes. Same two GPUs, so the comparison is fair.
speed

What you trade: the KV-cache transfer adds a little to the time to first token and needs a fast link (NVLink inside a server, InfiniBand between servers), and the gain depends on load and on that link. In return, decode runs without stalls, so the time per output token stays steady, and each pool can be sized, split (section 04) and even built from different GPUs for its own job. It pays off most for long prompts with moderate-length answers. It was introduced by research systems such as DistServe and Splitwise and is supported today by NVIDIA Dynamo, TensorRT-LLM, vLLM and SGLang.

What modern LLMs change

A3

How a model knows word order: RoPE

Attention scores a pair of tokens with q · k, which compares their content only. On its own it cannot tell "dog bites man" from "man bites dog". RoPE (rotary position embedding) fixes that by turning q and k by an amount set by each token's position. This chapter builds the idea one step at a time; section 00.3, step 6, shows where it sits in the forward pass. For runnable code, see the RoPE notebook.

A3.1

Rotate, don't add

A rotation needs two numbers, an x and a y, so q is cut into pairs: numbers 0–1, 2–3, and so on. Each pair is a small arrow. A token at position m has each arrow turned by m × speed. Nothing here is learned: the turn depends only on the position, never on the word.

  • Every token at the same position gets exactly the same turns, whether it is a q or a k, and in every head and layer. It is like a stamp that says "position m".
  • The words themselves differ, so the stamped arrows still point in different directions.
  • Turning never changes an arrow's length, so the content survives.
  • V is never turned: position should change who a token attends to, not what gets passed along.
word
A3.2

Same gap, same score

Now take two tokens: q at position m (the token doing the looking) and k at position n (the token being looked at). Each is turned by its own position, so they turn by different amounts. A dot product only cares about the angle between two arrows, and that angle changes by (m − n) × speed. The absolute turns cancel out; only the gap survives.

  • Same gap, same score: the model learns a rule like "the subject is one word back" once, and it works at position 5 or position 10,005.
  • Different gap, different score: "dog" one word before "bites" scores differently from "dog" one word after it, so word order is recoverable.
A3.3

Why every pair has its own speed

Angles wrap around. At 30° per position, position 12 has turned 360°, which looks exactly like position 0, so "1 word away" and "13 words away" would look the same. Using one very slow speed instead would never wrap, but neighbouring positions would differ by a fraction of a degree, too little to change any score.

RoPE gives each pair its own speed, from fast to slow. Different parts of the same vector then change by different amounts: the fast pairs tell neighbours apart, and the slow pairs keep long distances unique. Like a ruler with both millimetre and kilometre marks. Pick two positions and see which pairs can tell them apart.

A3.4

The real speeds

A real head has d_head = 128 numbers, so 64 pairs. Pair i turns by 10000−i/64 radians per position: about 57° for pair 0, and each next pair about 0.87 times slower, so the speed drops 10× every 16 pairs. The 10000 is a fixed setting called the RoPE base; models built for very long inputs raise it so the slowest pairs turn even more slowly.

The full recipe: compute q and k as usual, cut them into pairs, turn each pair by position × that pair's speed, then take the ordinary dot product. That dot product is the sum of 64 small ones, one per pair, so every pair adds its own view of the distance to the score. Shapes do not change.

A4

Fine-tuning with LoRA

Fine-tuning means training an existing model a little more so it gets better at one job, such as answering in your company's style. Updating every weight is expensive: for a 7-billion-parameter model, training needs about 16 bytes per weight (section A1), so roughly 110 GB before any activations. LoRA (low-rank adaptation) freezes the original weights and learns a small add-on next to some of the weight matrices instead. This chapter shows its shapes, where it goes, what happens during training, and the two ways to serve it.

A4.1

The shapes: a big frozen matrix plus two thin ones

Take one weight matrix W of shape [d_in, d_out], for example a query projection of [4096, 4096]. Full fine-tuning would learn a change ΔW of that same size. LoRA assumes the change is simple enough to write as the product of two thin matrices:

  • A has shape [d_in, r] and squeezes each token's d_in numbers down to just r numbers.
  • B has shape [r, d_out] and expands those r numbers back to d_out.
  • r is the rank, a small number you choose, typically 8 to 64.

The layer's output becomes y = x·W + (α / r)·x·A·B. α (alpha) is a fixed scaling setting. B starts at all zeros, so at the first step the add-on contributes nothing and the model behaves exactly like the original. Drag the rank to see how few numbers LoRA trains.

matrix
A4.2

Which layers get an adapter

LoRA can sit next to any weight matrix. In each transformer block there are seven candidates: the four attention projections (q, k, v and the output o) and the three MLP matrices (gate, up and down). You choose which ones, and the same choice repeats in every one of the L blocks. The pair of matrices A and B for one weight is called an adapter; all of them together are often called "the LoRA".

Embeddings, norms and the LM head are usually left alone. Adapting more matrices gives the add-on more room to learn, at the cost of more trainable numbers. The counts below are for Llama 2 7B (32 blocks, h = 4096, MLP width 11,008).

A4.3

What happens during training

The forward pass runs both paths: the frozen W and the small A·B detour, added together. The backward pass still sends gradients through W, because earlier layers need them, but W itself is never updated. Only A and B receive updates, so only they need gradients kept and optimizer state (the extra numbers Adam stores for every trained weight). That is where the memory saving comes from. Step through it.

speed
A4.4

Serving: merged vs separate adapters

After training there are two ways to use the adapter.

  • Merged: compute W′ = W + (α / r)·A·B once and save it as an ordinary weight matrix. The model has exactly the original shapes, so it runs at exactly the original speed. But each fine-tune is now a full separate copy of the model.
  • Separate: keep the one shared base W and add the small x·A·B detour at run time. That costs a little extra compute per token, but adapters are tiny files you can swap in and out. One server can hold one copy of the base and many adapters, and even give each request in a batch a different one.

Rule of thumb: one fine-tune that serves heavy traffic, merge it; many fine-tunes (one per customer or task), keep them separate on a shared base.

X1

Activation functions: ReLU, GeLU, SiLU, SwiGLU

An activation function (written act) is a simple curve applied to each number on its own, between two matrix multiplies in the MLP. It is not a multiplication. Without it, two matrix multiplies in a row collapse into one (W₁ then W₂ is the same as the single matrix W₁·W₂), and the model could only learn straight-line relationships, however many layers it had.

  • ReLU: keep positive numbers, set negative ones to 0. Simple, and the original choice.
  • GeLU: like ReLU but smooth around 0, and lets small negative values leak through a little. Used by GPT-2 and BERT.
  • SiLU (also called Swish): x times a smooth on/off switch, very close to GeLU in shape. Used inside Llama-style models.
  • SwiGLU is not a single curve but a gated MLP: one matrix produces values, a second produces a gate passed through SiLU, and the two are multiplied number by number before W₂ shrinks the result. That is why Llama-style MLPs have three matrices (gate, up, down); section A2 draws it.

X2

LayerNorm vs RMSNorm

Normalisation rescales each token's h numbers so they stay in a steady range from layer to layer. Both versions work on one token at a time.

  • LayerNorm: subtract the mean μ of the token's numbers, divide by their spread σ, then apply a learned scale γ and shift β. Result: centred on 0, spread of 1.
  • RMSNorm (root-mean-square normalisation): skip the mean. Divide by the root mean square (the typical size of the numbers), then apply γ. One less step, and it trains just as well, so Llama, Mistral and most recent models use it.

ε is a tiny number added before the square root so nothing is ever divided by zero. Below, γ = 1 and β = 0 so you see the normalisation itself.

X3

Softmax and temperature

Softmax turns a list of scores (any numbers, positive or negative) into weights that are all positive and add up to 1. Two steps: raise e to the power of each score, so bigger scores grow much bigger and everything becomes positive; then divide each result by their total. Attention uses it to turn match scores into shares (section 00.2), and the LM head uses it to turn logits into next-token probabilities.

Temperature divides the scores before softmax. Below 1 it sharpens the weights towards the top score; above 1 it flattens them. Dividing attention scores by √d_head works the same way: it keeps scores from growing with d_head, so softmax does not put almost all the weight on one token.

X4

Dot product, matrix multiplication, GEMM and GEMV

  • A dot product takes two lists of the same length, multiplies them number by number and adds the results: one number out. q · k in attention is a dot product.
  • A matrix multiplication (matmul, written A·B) does a dot product for every row of A with every column of B. If A is [m, n] and B is [n, p], the result is [m, p], and the inner sizes (n) must match. A transpose (ᵀ) only flips a matrix so those sizes line up.
  • GEMM (general matrix-matrix multiply) is the name of the library routine that does this on a GPU. When many tokens are processed together, as in prefill or training, the work is a GEMM and the GPU's arithmetic units stay busy.
  • GEMV (general matrix-vector multiply) is the special case where one side is a single row. Decode for one sequence is a GEMV: every weight is read from memory for just one row of work, which is why decode is limited by memory, not arithmetic (section 01).
X5

Glossary

Short definitions of terms used across the page. Words with a dotted underline anywhere on the page link here.

pipeline bubble
Time in pipeline parallelism when a GPU sits idle, waiting for the stage before it (at the start) or after it (at the end). With p stages and m microbatches it is (p − 1) / (m + p − 1) of the total time.
microbatch
A small slice of a batch. Pipeline parallelism sends microbatches through the stages one after another, so different GPUs can work on different slices at the same time.
latency
How long one request takes from start to finish, as one user feels it.
throughput
How much work the whole system finishes per second, for example tokens per second across all users. Batching raises throughput, often at some cost to latency.
compute-bound
The GPU's arithmetic units are the bottleneck: they are busy all the time. Prefill and training usually are.
memory-bound
Moving data from memory is the bottleneck: arithmetic units wait for numbers to arrive. Decode usually is, because every weight is read for very little work.
HBM
High-bandwidth memory: the GPU's large main memory (tens of GB) where weights and the KV cache live. Fast, but far slower than on-chip SRAM.
SRAM
Tiny, very fast memory on the GPU chip itself (a few MB). FlashAttention keeps its working tiles here.
NVLink
NVIDIA's direct GPU-to-GPU link inside one server. Much faster than the network between servers, so heavy communication (tensor parallelism) is kept within it.
InfiniBand
A fast network that connects servers. Slower than NVLink, so lighter communication (pipeline or data parallelism) crosses it.
All-Reduce
A communication step where every GPU contributes a partial result and every GPU ends up with the sum of all of them.
Reduce-Scatter
Like All-Reduce, but each GPU ends up with only its own slice of the sum. Half of an All-Reduce.
All-Gather
Every GPU shares its slice and every GPU ends up with all slices joined together. The other half of an All-Reduce.
replica
A full copy of the model on another GPU or group of GPUs. Data parallelism runs several replicas side by side.
activations
The in-between numbers that flow from one layer to the next, such as X, Q or the MLP's ffn-wide output. They depend on the input, unlike weights. Defined in section 00.3. Not to be confused with the activation function (act, Extras X1).
activation memory
Memory used to keep activations from the forward pass so the backward pass can use them. A training cost; inference keeps only the KV cache.
recomputation
Saving memory in training by not storing some activations and recomputing them during the backward pass instead. Trades extra compute for memory.
residual stream
The running total each token carries through the model. Every attention and MLP step adds its result to it instead of replacing it.
logits
The raw scores the LM head gives every vocabulary entry, before softmax turns them into probabilities.
W_U
The LM head's weight matrix, [h, V]. U stands for unembedding: it maps a hidden state back to one score per vocabulary entry, the reverse of the embedding table.
optimizer state
Extra numbers the optimizer keeps for every trained weight. Adam keeps two (running averages of the gradient and of its square).
utilisation
The share of time the GPU's arithmetic units are actually doing work.
